## Phase Goal

**As a** 部署与运维 ontoforge 的开发者兼管理员, **I want to** 让加载的 ontology 自动生成并安全演进按类型强类型的 edit store、每次写入都追加不可变 edit log，并用 roles-as-code 配置用户 / 组 / 角色与 CEL 行谓词、用 OIDC JWT 或 dev token 认证, **so that** 后续的 scoped 读与 Action 写建立在同一份可审计的数据和同一套「SQL 编译与 Rust 求值结果一致」的授权规则之上。

> 来源说明：ROADMAP Phase 3 的 `**Goal:**` 行不是 user story 格式。按 Phase 1 / 2 先例（`02-01-PLAN.md` Phase Goal 节）由 Goal 原文组成：actor 取自 Core Value 中的「应用 / 管理员」，capability 取自 Goal 前半句，outcome 取自 Goal 后半句与 Core Value。ROADMAP 原文未改写。

<objective>
Phase 3 的依赖与 crate 图前置：先经人工核验两个名称来源为 [ASSUMED] 的 crate，再一次性声明全部新依赖、修正 crate 依赖方向（删除 storage → query，新增 auth → engine、storage → {auth, expr, engine}），并用一个最薄的端到端 tracer 证明这套依赖在 Windows 本机真的能跑：storage 打开带 `recursive_triggers` 与 engine collation 的 SQLite 连接，auth 用 aws-lc-rs 后端签发并校验一次 JWT。最后加供应链守卫（无 openssl / native-tls）与 ADR-0023。

Purpose: STORE-01（双后端驱动与 sea-query）、AUTH-01（JWT crypto 后端）的前置；后续 17 个 plan 不再改任何 Cargo.toml / Cargo.lock，wave 内并行不会在 lockfile 上冲突。
Output: workspace 依赖、5 个 crate 的 manifest、storage 的 SQLite 连接选项、两个冒烟测试、CI 守卫、ADR-0023。
</objective>
