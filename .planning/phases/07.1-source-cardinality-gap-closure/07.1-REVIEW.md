### CR-01: 计数别名遮蔽物理 FK 列，导致样本排序与集合错误（已修复）

**Classification:** BLOCKER（历史严重度，当前 resolved）  
**Disposition:** `490adcbcdc6154529adfc30ef849f304208d6f87` 修复；`a78ad58` 增量复核关闭。下述问题与最初复现对应 `b942b55`，不是最终源码仍然存在的缺陷。  
**File:** `D:/DataSpellProjects/ontoforge/crates/ontoforge-engine/src/cardinality_check.rs:91-93`  
**Related lines:** 同文件 `113-119`、`149-150`  
**Issue:** 当合法 binding 把 FK 映射为物理列 `n` 时，projection 的 `count(DISTINCT ...) AS "n"` 与该物理列同名。`ORDER BY "n" ASC` 优先解析为输出别名，第二排序键实际仍是计数，而不是 FK。这使 `LIMIT 21` 在对象数相同的组之间没有 FK 排序保证；改变索引即可改变前 20 个样本的顺序与集合。Plan 01 明确要求“按对象数降序、FK升序稳定排序”，现有普通列名和 quoting 测试没有覆盖这种合法标识符冲突。

**实际复现:** Python `sqlite3`，SQLite `3.53.4`，内存数据库。下列 SQL 是当前 AST 对 `primary_key=id`、`foreign_key=n` 的同形查询，省略了与排序解析无关的 catalog/schema 限定。

```python
import sqlite3

connection = sqlite3.connect(":memory:")
connection.execute("CREATE TABLE records(id TEXT, n TEXT)")
connection.executemany(
    "INSERT INTO records VALUES (?, ?)",
    [(str(i) + suffix, chr(65 + i)) for i in range(25) for suffix in ["a", "b"]],
)
query = """
SELECT n AS fk, count(DISTINCT id) AS n
FROM records
WHERE n IS NOT NULL
GROUP BY n
HAVING count(DISTINCT id) > 1
ORDER BY count(DISTINCT id) DESC NULLS LAST, n ASC NULLS LAST
LIMIT 21
"""
print(connection.execute(query).fetchall())
connection.execute("CREATE INDEX n_desc ON records(n DESC)")
print(connection.execute(query).fetchall())
print(connection.execute(query).fetchall()[:20])
```

实测无索引返回 `A..U`，创建降序索引后返回 `Y..E`，每组计数均为 `2`。scanner 丢弃第 21 项后报告 `Y..F`；要求的 FK 升序样本应是 `A..T`。相同数据的冲突判定仍成立，但报告展示的样本不满足排序合同。这是 SQL 执行层的事实，不冒称已在 Rust engine 或真实 Trino 重现。

**Fix:** 消除聚合输出别名与输入列的解析歧义。最小方案是删除不被 scanner 解码依赖的 projection aliases，让第二排序键解析为输入 FK；也可显式按唯一的 FK 输出别名排序。不要改动 COUNT DISTINCT、NULL、20+1 或预算合同。增加 `foreign_key=n` 的回归，覆盖相同计数的 21 组以上数据；真实后端可用降序索引或打乱输入暴露缺失的排序键。若 SQLite fixture 没有建索引入口，至少用 printer 结构断言证明第二排序键不会被计数别名遮蔽，并由既有真实 Trino owner 补执行证据。

**最终修复与复核:** 保留 projection alias，两个排序键均明确引用输出名，生成 `ORDER BY "n" DESC NULLS LAST, "fk" ASC NULLS LAST`。生产 diff 只有两个 `OrderItem.expr`，未改变聚合、映射、NULL、预算或退出码。真实 Trino 在只修第二键时揭示同根因的第一键错误：PK=`fk` 时原 `ORDER BY count(DISTINCT fk)` 报 `Invalid reference to output projection attribute from ORDER BY aggregation`、CLI exit3；这一事实纳入同一 CR-01，两个输出 alias 的最终方案同时消除两处歧义。

**Issue:** 测试等待 `fixture.deletes > 0` 后立即断言 active probe 已从 `queries` 删除，但 mock responder 在第54行先 `deletes.fetch_add`，之后才在第69行获取 `queries` mutex 并删除条目。合法交错为：responder 发布 DELETE 计数后被暂停；测试读到非零计数，先获得 queries mutex，读到尚未删除的 active_probe，导致新增断言失败。`SeqCst` 只约束 atomic 操作顺序，不保证发布计数之后的删除已经完成。该问题影响测试可靠性，尤其本次修正正在处理高负载下的异步测试波动。
