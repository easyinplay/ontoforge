## Phase Goal

**As a** 部署 ontoforge 的开发者, **I want to** 把 object type 与 M:N link 绑定到已有 Trino 的物理表，并用 `ontoforge validate --online` 校验绑定, **so that** 应用与 agent 读到的是企业已有的数据，而 Windows 本机无需 Trino 即可用 SQLite 替身跑通全部测试。

> 来源说明见 02-01-PLAN.md 的 Phase Goal 节。

<objective>
本 plan 是 phase 级的端到端 tracer：第一次把定义层（02-03）、引擎层（02-02）与 CLI 接成一条线——`ontoforge validate --online` 读取选定 profile 的绑定，把 fixture 加载进 SQLite 替身，逐个描述物理表、比对绑定，并把不匹配映射成带绑定文件 line:col 的 ONT-V17。随后补齐 fixture 语义（JSON、NULL、按类型转换、decimal 不舍入、时区、数组、ATTACH 上限）与 aviation 的完整演示数据。

Purpose: BIND-03（`validate --online` 校验绑定）、ENGINE-04（SQLite 替身支撑 Windows 本机测试与后续 `serve --dev`）。
Output: `online.rs`、`--online`、`bind_check` 模块、`sqlite/fixture.rs`、CLI 与引擎测试、aviation fixture 数据。
</objective>

本 plan 的取舍（Claude's Discretion，执行时不要改回）：
- 本 plan 的 `compare_binding` 只判断「表是否存在、列是否存在、类型族是否相同」；族划分为 integer（tinyint / smallint / integer / bigint）、float（real / double）、decimal（decimal / number）、string（varchar / char）、boolean、date、timestamp、array、其他。02-08 在不改变「跨族即 error」的前提下补齐族内规则。
- 物理列名比较一律小写化（Trino 以小写暴露标识符，RESEARCH Pattern 6）。
- 替身表的存储类型：string / decimal / date / timestamp / array 存 TEXT，整数与 boolean 存 INTEGER，float / double 存 REAL；对外报告的 `PhysicalColumn` 用 Trino 规范类型（`varchar`、`decimal(P,S)`、`timestamp(3)` 或 `timestamp(3) with time zone`、`array(T)` 等），fixture 中未映射的多余列报告为 `varchar`。
- fixture 上限：单文件 4 MiB、100 000 条记录；不同 `catalog__schema` 至多 10 个；两个不同 (catalog, schema) 映射到同一库名时报错。
- 本 plan 中引擎错误（`EngineError`）统一映射为 ONT-V19 + 退出码 3；Trino 路径与相应测试在 02-09。
