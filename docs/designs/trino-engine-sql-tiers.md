## Problem Statement

企业要把真实业务操作交给 AI agent，但现有做法守不住边界：对外 agent 即使只被允许执行 DQL，推理过程仍会暴露真实后台表名，并能写出越过自身 scope 的查询。同时，内部技术人员需要直接用真实表 + ontology 知识高效取数。ontoforge 要成为一个**通用**的、可自托管的 ontology 操作层：同一份 ontology 既是 agent 的受控读取边界，又是唯一受控写入入口，并且 ontology 本身主要由 AI 维护、由人审批。

核心承诺（头号验收标准）：**L0 / L1 的任何查询路径和任何 Action 都无法逃逸调用者的 scope**（scope 定义见「Scope 模型」）。L2 / L3 是授予受信主体的显式例外，其边界只到 catalog / schema 级并全量审计（见「SQL 级别」）。

## Demand Evidence

- 用户所在公司已经自研并运行过一个 ontology 产品，服务对内、对外系统以及员工自用的 agent CLI。
- 真实故障模式（用户原话）：「对外的系统中如果不分层，agent的思考步骤中就会暴漏真实的后台数据表，虽然对外的做了agent只能执行DQL的能力，但依然存在着越权写sql查询不属于自己scope的可能。」
- 内部场景的相反需求：「内部人员用的时候很多场景下他们对内部表更熟悉，有时候拿着ontology本身的知识+自身的理解，用起来更方便。」
- 使用方结构：「ontology很大程度上是给AI用的，不是给人用的」；ontology 的管理修改大部分也由 AI 完成，人需要管理配置页面来干预与审批。
- 缺口：目前证据全部来自一家公司内部；外部需求（开源社区开发者）尚未验证。

## Status Quo

公司现有 ontology 产品与自有业务绑定太深，技术栈 / 性能 / 部署方式无法通用化，因此重做通用产品（用户原话：「我们之前的系统跟我们自有业务绑定太深」）。外部同类：语义层（Cube 等）只解决受控读取、不管写入；Palantir Foundry 闭源且需要把数据整合进平台。

## Target User & Narrowest Wedge

- 第一批外部用户：开源社区开发者（尚无具体姓名，是本设计最大的需求缺口）。
- design partner：用户所在公司（只作为真实场景与数据的测试场）。
- 最窄切入：一个能在公司对外系统里替换现有做法的「可验证 agent 权限边界」，读（L0/L1）与写（Action）同时受同一套 scope 约束。

## Constraints

- 通用系统：公司场景与数据只作为私有测试 fixture；核心代码、公开示例、默认配置、命名不得绑定公司。
- Windows 11 本机 `cargo build` / `cargo test` 必须通过，不依赖 Docker。
- 技术栈沿用已锁定选型（Rust 1.98 / axum / sqlx / sea-query / cel / rmcp），变更须走新 ADR；加功能先查现成 crate。
- 不复制参考仓库代码（mcp-trino 只借工具设计，用 `rmcp` 重写）。

## Premises（用户已确认，含修订）

1. ontology 的主要使用方是 AI；人通过管理界面配置、干预、审批。AI 也修改 ontology 本身，因此每次变更先过 validate / lint，再走「提议 → 人审批 → 生效」。
2. 不受信 agent 只能用 L0 / L1，永远看不到物理名。L1 由服务端解析并编译成确定的 Trino SQL，scope 谓词在编译期注入（隐藏表名不等于授权）。L2 只给受信主体。
3. 写入只走 Action，按 action type 配置写入模式：`online`（写 PG edit store）或 `batch`（Nessie 分支上直写 Iceberg 后 merge，action log 记录主体、参数、影响行数与 Nessie commit id）。edit log 长期归档可落 Iceberg。
4. **Trino 是必需的外部计算平台，ontoforge 只带连接能力，不打包、不托管 Trino 部署。** Iceberg / Nessie / 对象存储 / Spark / Doris / Kyuubi 为可选附加组件。PG 存 ontology 系统数据。内置替身引擎用于测试与 `serve --dev` 本地演示，不承诺生产（修订：原文为「仅服务 cargo test」，因 Phase 6 单二进制演示需要而扩展，用户已确认）。
5. 差异点：读写同一个 ontology、AI 维护 + 人审批、单二进制服务、接入企业已有数据平台。

## Cross-Model Perspective

独立 cold read（Codex）：
- 最强版本：ontoforge 是企业 AI 的业务操作边界，agent 经稳定业务对象读取、经受控 Action 改变状态，权限与审计贯穿读写。
- 关键洞察：越权 DQL 说明首要产品是「可验证的 agent 权限边界」；隐藏表名不构成授权。（已采纳为头号验收标准。）
- 挑战的前提：「生产必需 Trino」会成为部署门槛。用户以「ontoforge 是服务、Trino 是集群平台、内化 Trino 后联邦 / ETL / L2-L3 依赖它」保留，并拒绝打包部署。风险转入 Open Questions。
- 原型建议的越权验收思路纳入 Success Criteria。

## Approaches Considered

- **A 当前 milestone 不变只定 seam**：否决。原计划的生产目标是 PG（通用 JSONB 表、tsvector 全文），业务数据进 PG；改为 Trino 后数据模型、全文、等价测试都要重做，且本 milestone 交付不了针对真实痛点的 scope 边界。
- **C 先做只读边界**：否决。写路径出来前与语义层无差别，打乱 Phase 1→2→3 依赖。
- **B 按 Trino 主引擎重排**：选定，见下。

注：查询层本来就是「自有 AST → 方言 renderer」（ADR-0005），所以 A 与 B 的差别不在编译器写几次，而在**生产目标引擎、业务数据存放位置、scope 模型是否本 milestone 交付**。

## Recommended Approach：B

### 1. 数据源绑定（新增，修订 ADR-0003，扩展 Phase 1 IR）

object type 增加可选的 `source` 声明，把对象映射到 Trino 的物理表：

```yaml
kind: ObjectType
apiName: Flight
primaryKey: flightId
source:            # 可选；缺省 = edit-only object type
  catalog: lake
  schema: ops
  table: flights
  columns:         # 属性 → 列；未列出的属性按同名列
    flightId: flight_no
    departureTime: dep_ts
properties: ...
```

- 物理名只出现在定义文件与 L2/L3，L0/L1 输入输出（含错误）一律只用 apiName。
- 无 `source` 的 object type 是 edit-only：数据只来自 Action，存在 PG edit store。
- link 的外键 / join 表同样可绑定物理列；M:N join 表可来自 source 或 edit store。
- IR 改动是新增可选字段，向后兼容；validate 增加：catalog 名合法性、列映射完整性（启动时可选对 Trino `information_schema` 做在线校验）。

### 2. 读路径与一致性（修复阻塞项 1）

> Eng review（2026-10-16）修订了本节，详见「Eng Review 决策」D2 / D4 / D12 / D13 / D17 / D18 / D22；下文为修订后的规则。

- **对象当前状态 = source 行（经 Trino）按属性叠加 edit（PG edit store）**，edit-only 对象只来自 edit store。两条执行路径、一份叠加规则（D2）：
  - get-by-pk 与 Action 前置读：PG 直读 edit store → 命中则按规则合并（未设置的属性需要时再经 Trino 单表 pk 查 source）；未命中 → Trino 单表 pk 查 source；合并、行谓词与列遮蔽在 Rust 内完成（CEL 单行求值，D12）。
  - list / filter / aggregate / searchAround：Rust 两段归并（D24，ADR-0020）—— Trino 只跑单表 source 查询，edit 经 PG 直连，按 pk ≤ 256 分批回查，在 Rust 内叠加、分页、分解聚合。
  - 叠加规则只有 Rust 一份生产实现，proptest 对照内存参考模型。
- **读后写一致**：PG 提交后下一条 Trino 查询必然可见（spike 3 A2.2 已验证）；edit store catalog 不得开启数据 / 结果缓存。
- **叠加规则（D17：按属性 patch，取代原「整行快照」）**：edit 行只存被 Action 设置过的属性，`set_mask` 标记哪些列有效；未设置的属性始终读 source（继续跟随 ETL）。tombstone 压制同 pk 的 source 行，不会「复活」，直到 release。release 是显式状态（D22），版本号单调递增、永不重置，release 后对象回到纯 source。ETL 删除了有 edit 的 source 行：对象以 edit 中已设置的属性存在、未设置属性为 null，并在 describe 中标记 source 缺失。重复 source pk 返回 `AmbiguousObject`（D18）。
- **版本令牌（D4 / D13）**：读返回不透明 `_version` token = HMAC(server_key, principal_id ‖ type ‖ pk ‖ 规范化(edit 行 + source 行))。未编辑对象内部版本为 0，第一次 edit 为 1。
- **Action 执行（D4 / D22）**：PG 事务外先经 Trino 读 source → 开 PG 事务，按 (type, pk) 稳定顺序锁 edit 读集 → 比对客户端 expected token → 写入。不再二次读 source；保证边界：前置读到提交之间的 source 变更不被检测（几百毫秒窗口，写入文档）。`command_id` 语义见 D-misc。
- materialize 到 Iceberg 推迟到下一 milestone；本 milestone 叠加读取即可闭环。

### 3. Scope 模型（修订 ADR-0008：行 / 列级安全提前进本 milestone）

scope 是核心承诺本身，因此把 PROJECT.md 原列为 v2 的行 / 列级安全提前。

- 主体：user、group（可同步自 OIDC `groups` claim）、role；role 绑定到 user 或 group。
- 每个 role 的授权项：
  - object type 可见清单；每个 object type 的属性 allow-list（列级）
  - 行过滤：CEL 谓词，变量为对象属性与主体属性，例：`object.tenantId == principal.attrs.tenantId`
  - action type 执行权
  - SQL 级别（L0-L3）与 L2 可访问的 catalog / schema 清单
  - MCP toolset
- 主体属性 `principal.attrs` 来源：JWT claim 按配置映射（如 `tenantId ← claims.tenant`），dev token 由 CLI 指定；缺失属性按 null 处理，相关谓词求值为 false（fail-closed）。
- 求值时机：编译期把行过滤 CEL 转成 SQL WHERE（复用 Phase 1 的 CEL 类型检查），属性 allow-list 裁剪 SELECT 列。
- 多 role 合并：按 role 分别编译 (行谓词 R_i, 列集 C_i)。行可见条件 = `R_1 OR … OR R_n`；列 x 只在授予它的 role 的行谓词成立时输出，即 `CASE WHEN (OR of R_i where x ∈ C_i) THEN x ELSE NULL END`，防止「A 的列 × B 的行」交叉泄露。
- scoped 基关系：编译器先为每个 object type 构造一个「已按行可见条件过滤、所有列已按上式遮蔽」的基关系，L1 与 object set 的一切表达式（WHERE、ORDER BY、GROUP BY、聚合、link join 键）只能绑定到这个基关系，不能引用原列，杜绝用谓词或聚合反推被遮蔽的值。规则写入 ADR-0008 修订，conformance 套件包含「谓词推断」用例。
- Action 写入前对目标对象做同样的行过滤检查；写入的属性必须在该主体对这一行可见的列集内。
- fail-closed：无授权 = 不可见；无法编译成 SQL 的 CEL 谓词在 validate 阶段报错。

### 4. SQL 级别

| 级别 | 主体 | 可见内容 | 执行方式 |
|---|---|---|---|
| L0 | 默认 | 授权内的 object / property / link / action（apiName） | describe、object set 查询、action 工具 |
| L1（下一 milestone，CEO review D1 推迟） | 被授予 `sql:ontology` | 同 L0 | 类 SQL，表名 = object type apiName；`sqlparser-rs` 解析，只接受 SELECT 子集，JOIN 必须沿已声明 link；转 ontology 逻辑计划 → 注入 scope → 渲染 Trino SQL |
| L2 | 被授予 `sql:raw` | 授权 catalog / schema 内的物理表 | 原始 Trino SELECT；ontoforge 校验（单语句、只读、catalog allow-list）后以只读服务身份执行 |
| L3 | 被授予 `sql:admin`，仅 CLI / 管理端，不对 agent MCP 暴露 | 全部 | 任意 SQL（含 ETL / DDL），全量审计 |

Trino 接入（用户决策，方案 A）：参考 `tuannvm/mcp-trino`（MIT，Go）的架构分层 —— 配置层 / Trino client 层 / MCP handlers 层。
- L2 工具层用 `rmcp` 重写，工具名与参数对齐 mcp-trino 的 6 个工具（`execute_query`、`list_catalogs`、`list_schemas`、`list_tables`、`get_table_schema`、`explain_query`），使用过 mcp-trino 的 agent 可直接迁移；在其上叠加 ontoforge 的 AST 白名单、结果上限、审计与身份透传。
- 借鉴其设计：schema allow-list（`TRINO_ALLOWED_SCHEMAS` 思路）、查询归属标签（`X-Trino-Client-Tags` / `X-Trino-Client-Info`）、可选的 `X-Trino-User` 身份透传、默认只读。
- 连接执行层：mcp-trino 依赖官方 `trinodb/trino-go-client`，Go 库无法链接进 Rust，因此按 spike 1 结论自写 Rust 薄 client（`reqwest` + rustls），同时服务 L0 叠加读、Action 前置读与 L2。不用 sidecar（破坏单二进制、只得 JSON 文本、无法取消与按请求透传身份），不用 FFI。
- 只借设计不复制代码（项目约束）。

L2 边界（显式例外）：
- scope 粒度只到 catalog / schema allow-list，对象级行 / 列安全不作用于 L2；这是把真实表交给受信主体的有意设计，文档与授权界面须明示。
- edit store 所在 catalog 硬编码排除在 L2 / L1 物理访问之外，只能经 ontology 叠加读取访问。
- 两个独立的 Trino 服务身份：「ontology 身份」用于 L0 / L1 / Action 的叠加读取（可访问 source catalog 与 edit store catalog）；「L2 身份」只用于 L2 执行，只读且只能访问 allow-list。下面的启动自检只针对 L2 身份。
- L2 默认以只读的 L2 身份执行；若部署方在 Trino 侧配置了访问控制，可开启按主体透传（`X-Trino-User` impersonation），由 Trino 施加更细粒度权限。
- **L2 硬依赖 Trino 侧权限（CEO review OV2）**：view 等间接引用只有 Trino 能约束，因此 L2 的开启前提是部署方已在 Trino 侧把 L2 身份限制到 allow-list（含 view 的实际执行权限），并在配置中显式声明。启动自检只做只读探测，通过条件是「访问 allow-list 外 catalog 与 edit store catalog 必须被 Trino 拒绝」；无法证明安全（探测成功或结果不可判定）一律禁用 L2 并报警（fail-closed）。
- ontoforge 自身校验是第一道防线：AST 白名单只允许 SELECT / WITH，禁止 `TABLE(...)` 表函数（含 JDBC connector 的 `system.query` 透传）、`CALL`、`EXECUTE`、会话 / 事务语句，解析不了的一律拒绝；部署文档要求各 connector 的数据库账号只读。L2 / L3 全量审计。

### 5. 引擎与测试

- 查询编译：ontology 逻辑计划（自有 AST，ADR-0005 不变）→ 引擎 trait → 两个 renderer：Trino（生产）与 SQLite（测试与 `serve --dev`）。
- 风险（明确接受）：Windows 本机测试覆盖不到 Trino 方言语义；Trino renderer 的正确性靠 Linux CI 的 Trino service container 集成测试 + 同一 conformance 套件（替身 vs Trino 结果等价，取代原 QUERY-08 的 SQLite vs PG 等价）。
- renderer 实现方式（D14，eng review 定案）：自有的小型类型化 printer，只覆盖编译器产出的子集；字面量 / 标识符只经两个转义函数；proptest + 真实 Trino / SQLite 执行验证。`sqlparser` 只用于 L2 输入校验与往返自检（spike 2 G37：sqlparser 无法解析 timestamptz / array cast，不能用于生成）。edit store 本身经 `sea-query` + `sqlx` 访问（PG / SQLite）。

## CEO Review 决策（2026-10-16，HOLD SCOPE）

范围：**B-boundary**。本 milestone = 数据源绑定 + Trino 叠加读 + online Action + scope 模型 + L0 + L2 Raw DQL + core / full toolset；L1 Ontology SQL 推迟（L0 已堵住越权 SQL，L1 补的是表达力，且越权测试面最大，应在 scope 模型经实战验证后再建）。

| # | 决策 | 内容 |
|---|---|---|
| 1A | Trino 不可用 | Action fail-closed，返回 `EngineUnavailable`（可重试、不写入）；`/health` 与 MCP describe 暴露引擎状态；超时可配 |
| 2A | 错误映射 | L0 返回结构化错误码 + apiName 级描述 + request_id，原始 Trino 错误只进服务端日志；L2 / L3 可见原始错误；conformance 含「错误不含物理名」 |

**`/plan-eng-review` 必须解决项**（来自 outside voice，原则已定，语义细节由架构评审锁定）：
1. source 并发：未编辑 source 行用内容指纹作为版本参与校验，提交前复核；外部 source 无法参与 PG 事务，写明保证边界与剩余竞态窗口。
2. 多对象约束：submission criteria 读到的对象形成读集，提交时校验读集版本（edit store 对象按 `_version`，source 对象按指纹）。
3. 写后授权：create / modify（含改 scope 相关属性如 tenantId）/ link 变更 / release edit 的结果状态必须对调用者可见，否则拒绝；link 两端都要检查。
4. 遮蔽与快照：Action 内部用未遮蔽的原始行构造快照，被遮蔽列原样保留不写 NULL；criteria、表达式与返回值只能引用调用者可见列；区分客户端可写字段与系统保留字段。
5. source 主键与类型契约：pk 必须非空且唯一（drift 校验含抽样或约束检查），重复 pk 时该 object type 降级；数值精度、时间类型、字符串比较规则写入绑定规范。
6. `command_id` 安全语义：作用域 = 主体；同键不同参数报错；返回缓存结果前重新鉴权；提交成功但响应丢失时可凭同键查询结果。

## Success Criteria

- 越权不可达：对每个 L0 / L1 路径与每个 Action 构造越权用例（换 ID、伪造主体属性、引用未授权对象 / 属性、多 role 列 × 行交叉、子查询 / CTE / 别名绕过、并发重复提交），全部被拒绝且错误不泄露未授权对象状态；L2 用例覆盖 allow-list 外 catalog、edit store catalog、多语句与写语句，全部被拒绝。用例进 conformance 套件，替身与 Trino 两端都跑。
- 不暴露物理名：L0 / L1 的所有输入输出（含错误信息）不出现物理 catalog / schema / 表 / 列名。
- 写路径：`online` action 原子提交、乐观并发、`command_id` 幂等、每次写入可在 edit log 审计；提交后下一次查询可读到；下游 webhook 收到对应事件（可重试、幂等）。
- 可观测：写入审计（edit log）与写入同事务、不可丢；所有级别查询都有元数据读审计，异步批量落库，进程崩溃时至多丢失约 1 秒，积压或持续写失败时读请求 fail-closed（`AuditUnavailable`，D15）；超限结果带 `truncated` 标记；Trino 不可用、schema drift、L2 自检失败都能从 `/health` 与日志看到。
- 公司场景验证：真实越权案例脱敏成私有 fixture，放在仓库外，通过 `ONTOFORGE_PRIVATE_FIXTURES` 环境变量指向，由维护者在内网环境手动或私有 CI 运行，验收以运行日志为准，不进公开 CI。
- Windows 本机 `cargo test` 全绿；Linux CI 的 Trino 集成测试全绿。
- 通用性：仓库公开部分不含任何公司专属名称或配置。

| D20 | reload 加固 | DDL 后 Trino `flush_metadata_cache` 并探测新列可见再切换定义；DDL `lock_timeout`，超时保留旧定义；新增 required 属性须带 default，否则按破坏性处理；`def_version` 栅栏拒绝旧定义写入 |
| D21 | L2 元数据泄露 | allow-list 硬排除 `system` 元数据表；启动自检「L2 身份读 `system.runtime.queries` 只见自己的查询」，否则禁用 L2 |
| D22 | 路径修正 | 先 Trino 后 PG 事务、稳定锁顺序；release 为显式状态；over-fetch 循环补取 + `has_more`（短页不等于结束）；列表 pk 去重；非快照一致边界写入文档 |
| D23 | 差分成本 / collation | 完整 proptest 只跑 Rust vs SQLite；Trino 端跑固定种子语料 + 历史反例；source 绑定可声明 collation，大小写不敏感列禁止下推字符串比较与排序 |
| D24 | 列表 / 聚合路径（spike 3b 后） | Rust 两段归并为主：Trino 只跑单表查询（source 谓词 + TopN 补取、按 pk ≤ 256 分批回查），edit 经 PG 直连；叠加、分页、可分解聚合（count / sum / avg 分解，min / max 走 TopN 补取，count distinct 分组计数或报错收窄）在 Rust 完成；scoped 编译用「role 谓词 AND 原列过滤、遮蔽只在投影层」形态；Trino 内叠加退为不承诺延迟的备选（ADR-0020） |
| D25 | 延迟预算（spike 3b 后） | 删除 resource group 前提（实测排队 ≤ 1ms）；安静或隔离集群下 pk 读 p95 < 500ms、列表 / 过滤 p95 < 1s、聚合 p95 < 1.5s、Action p95 < 1s、已编辑对象 PG 直读 p95 < 50ms；ontoforge 强制 Trino 查询单表、≤ 2 fragment；繁忙共享集群只监测不承诺，繁忙对照列为 CI / 私有 fixture 验证项 |

自决项（D-misc，按「决策自主」原则，用户可否决）：`command_id` 表 `action_commands` 唯一键 `(principal_id, command_id)` + `params_hash`，同键异参 `CommandIdReused`，回放前重新鉴权，`get_command_result` 查询，默认保留 7 天；webhook 用事务性 outbox，至少一次投递，`event_id` 幂等；SQLite 替身以 `ATTACH` 库名 `catalog__schema` 映射 catalog；edit store 索引 = pk + 行谓词引用属性 + `indexed: true` 属性；叠加列表页上限 200；Trino client keep-alive 池、`nextUri` 退避、断连 `DELETE` 取消；PG catalog `statistics.enabled` 作为 CI 探针核实。
